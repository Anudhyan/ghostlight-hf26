# Publication checklist

This is a preparation checklist, not a claim that an entry has been submitted.

Challenge: https://dev.to/challenges/hacktoberfest-week4-2026-10-26

Week 4 rules: https://dev.to/page/hacktoberfest-week4-2026-10-26-contest-rules

Deadline: **31 October 2026, 11:59 PM PDT = 1 November 2026, 12:29 PM IST / 06:59 UTC.**

## Verify the project

- [x] Confirm the real model loads and semantic retrieval completes in a supported browser. Fresh Chromium/WASM preview check: 1 November 2026, two expected paraphrase results and one unrelated query.
- [x] Inspect the earlier real CPU-inference results and run the five archive/vector checks. No mocked output was used for browser inference.
- [x] Check adding, importing, exporting, optional persistence across reload, removing the fictional test note, and returning to session-only mode. The full forget/reset path was not repeated in this run.
- [ ] Check the interface on a small screen and with keyboard controls.
- [ ] Confirm the new project's source repository was created within this challenge's window. The attached repository from 2023 cannot be reused as the challenge project.
- [ ] Publish the code to a repository judges can access and replace the single `{{CODE_REPOSITORY_URL}}` marker in `docs/dev-post.md`.
- [ ] Confirm the deployed demo succeeds and can be opened by judges without special access, **or** provide an accessible video walkthrough. A private deployment or source zip alone is insufficient.
- [ ] Remove the README's provisional demo-publication note once public access is verified.

## Review the DEV draft

- [ ] Use the challenge template sections: What I Built, Demo, Code, How I Built It, and Why Does Open Innovation Matter?
- [ ] Preserve the required `devchallenge` and `hf26challenge` tags.
- [ ] Keep the source, model/runtime credits, factual privacy limits, and AI-assistance disclosure.
- [ ] Verify every capability described against the final application. Add real validation results only after they have been observed.
- [ ] Do not claim a partner prize category unless the project meaningfully uses that partner's technology.
- [ ] If there are human teammates, list their DEV handles. Publish only one submission for the team.
- [ ] Confirm the entrant meets the official eligibility rules and has an active DEV account in good standing.
- [ ] Check no unresolved URL markers or editorial instructions remain.

## Publish and confirm

Authenticated DEV publishing access is not available in the prepared environment. No post has been published by creating these files. The account owner must use an authenticated DEV editor or provide a supported publishing connection.

1. Open the challenge's Submission Template link while signed in to DEV.
2. Copy the reviewed article body from `docs/dev-post.md`, set the title and required tags, and preview formatting and links. The frontmatter marks the file as a draft; do not paste it into the rendered article body if the editor uses separate title/tag fields.
3. Publish before the deadline. The challenge requires a **published** post; a saved draft is not a submission.
4. Open the resulting post URL and confirm the correct tags, demo, and repository links are visible.
5. Save that published URL as proof of submission.

The contest only counts the first submission. Avoid publishing a second replacement entry without checking the official rules. Disclose any source commits after the deadline in the README's post-deadline change log.
